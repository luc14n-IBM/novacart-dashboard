The application is a three-tier web application composed of a React single-page application, a Python REST API, and a SQL data backend. In production it runs as three co-located containers inside a single SPCS service spec. Locally, the same backend and frontend processes run directly on the developer's machine against a bundled SQLite database, with no Snowflake account required.

1. Frontend React / JS

TechnologyVersionRoleRationale
React ^18.3.1 UI framework — component model, state, routing Industry-standard SPA framework. React 18 concurrent rendering ensures the UI remains responsive while multiple API calls resolve in parallel via Promise.all.
React Router DOM ^6.28.0 Client-side routing between Login, Orders, Products, and Customers views Enables a multi-page feel without full-page reloads. The /login guard redirects unauthenticated users; all unknown routes redirect to /login by default.
Recharts ^2.15.0 Data visualisation — bar charts, line charts, tooltips React-native charting library built on SVG. Chosen over Chart.js for its declarative JSX API that integrates cleanly with React's component model. Used for monthly revenue bars, top-products bars, and geographic revenue charts.
Vite ^6.3.5 Build tool and local development server Replaces Create React App. Provides near-instant HMR via native ES modules, a built-in /api reverse proxy for local development (eliminating CORS setup), and fast production builds via Rollup. The proxy rewrites /api/* to http://127.0.0.1:8000/*, mirroring the NGINX router in production.
@vitejs/plugin-react ^4.3.4 JSX transform and React Fast Refresh for Vite Official Vite plugin that enables React JSX compilation and hot module replacement during development.

Key frontend design decisions

  • Global date state in App.jsx — startDate and endDate are lifted to the root component so that changing the date filter on one view persists when navigating between views. All three data views receive these as props.
  • Single API client module (src/utils/api.jsx) — all fetch calls are centralised here. This makes the base URL (VITE_BACKEND_URL) configurable in one place and makes the entire HTTP layer mockable in tests.
  • Dark/light theme via ThemeContext — theme preference is managed in React context and applied via CSS custom properties, avoiding inline style proliferation across components.
  • 5-minute polling interval — all data views set a setInterval of 300 000 ms to refresh data, keeping the dashboard live without a manual reload.
  • Cache strategy — data endpoints use cache: "no-cache" to always revalidate with the server. Static endpoints (/health, /authorize) use the browser default to allow short-term caching.

2. Backend Python / FastAPI

TechnologyVersionRoleRationale
Python 3.11 Runtime language for the API server Python 3.11 is the current stable LTS-equivalent release with performance improvements over 3.10. Pinned in both the Dockerfile (ubi9/python-311-minimal) and the CI workflow (setup-python@v5) to ensure consistent behaviour across environments.
FastAPI 0.111.0 REST API framework — route definitions, request validation, auto-generated OpenAPI docs FastAPI's async-capable, type-annotated approach generates Swagger UI at /docs automatically, which serves as live API documentation. All query parameters (start, end) are declared as typed function arguments and validated by Pydantic without any boilerplate. CORS middleware is conditionally applied only in Dev mode.
Uvicorn 0.30.1 [standard] ASGI server — production-grade HTTP server for FastAPI The standard extras include httptools and uvloop for improved throughput. Runs on 0.0.0.0:8000 inside the container (all interfaces, as required by SPCS inter-container networking) and on 127.0.0.1:8000 locally.
python-dotenv 1.0.1 Loads .env file into environment variables for local development No-op in production (SPCS injects env vars directly). Allows developers to configure DATA_BACKEND, SQLITE_PATH, and CLIENT_VALIDATION without modifying code. .env is excluded from version control via .gitignore.
httpx 0.28.1 HTTP client — required transport layer for FastAPI's TestClient Dev/test dependency only. FastAPI's TestClient uses httpx internally to dispatch requests to the ASGI app in-process, with no live server required.

Authentication design

The backend operates in two modes, controlled by the CLIENT_VALIDATION environment variable:

  • Dev mode — GET /authorize returns a mock user (dev_user) without any header check. CORS middleware is enabled to allow local frontend requests from localhost:3000.
  • SPCS / Prod mode — Snowflake injects the authenticated user's identity into the Sf-Context-Current-User request header. The /authorize endpoint reads and returns this header. Requests without it receive a 422 Unprocessable Entity. CORS middleware is disabled — all routing is handled by the NGINX router.

3. Data Layer SQL

TechnologyEnvironmentRoleDetails
SQLite (stdlib) Local development Embedded SQL database for local development — no server required data/novacart_gold.db is committed to the repository. Contains 30 000 orders, 400 customers, and 15 products. The Python sqlite3 module is used via sqlite3.Row for dict-like row access. No additional package required.
Snowflake SPCS production Cloud data warehouse — Gold layer source of truth for all production data The NOVACART_DB.APP schema contains the same four-table Gold schema as the local SQLite file. Queries use %s parameter style. Results are normalised to lowercase keys in connection.py for compatibility with the SQLite code path.
snowflake-connector-python SPCS production Official Snowflake Python driver 3.11.0. Supports OAuth token authentication (SPCS mounted token at /snowflake/session/token) and keypair authentication (local Snowflake connections). DictCursor is used to return rows as dicts, consistent with the SQLite path.

Gold layer schema

TableKey columnsPurpose
fact_ordersorder_id, customer_id, product_id, order_date, amount, status, quantity, date_keyCentral fact table. Revenue calculations filter on status IN ('delivered', 'shipped').
dim_customercustomer_id, name, addr_city, addr_state, is_currentType-2 slowly changing dimension. Queries filter is_current = 1 to select the active record.
dim_productproduct_id, name, category, priceProduct reference — joined to supply name and category fields.
dim_datedate_key, year, month, month_nameDate dimension joined to fact_orders for monthly grouping in the orders endpoint.
Design decision — dual backend abstraction: connection.py provides a single get_connection() / execute_query() interface that transparently switches between SQLite and Snowflake based on DATA_BACKEND. Route handlers in main.py call only these two functions and have no direct dependency on either driver. This means all seven endpoints can be integration-tested against SQLite in CI without any Snowflake credentials.

4. Infrastructure & Deployment Containers / SPCS

TechnologyVersion / SourceRoleDetails
Docker — Container runtime — builds and packages all three services Three independent Dockerfiles produce three images that are pushed to the Snowflake image registry and deployed as a single SPCS service with one spec file.
Backend base image registry.redhat.io/ubi9/python-311-minimal:latest Minimal Red Hat UBI Python 3.11 image for the FastAPI container Sourced from Red Hat's registry per IBM security policy. Runs as non-root user 1001. Minimal image reduces attack surface and image size.
Frontend build image node:18-slim (build stage) Compiles the React application via npm run build Multi-stage build — the Node image is used only for compilation. The compiled static assets are copied to the serve stage; Node never ships to production.
Frontend serve image nginx:alpine (serve stage) Serves the compiled React static bundle Lightweight NGINX on Alpine. Configured with try_files $uri $uri/ /index.html to support React Router's client-side navigation. Listens on port 3000.
NGINX Router image nginx:alpine Reverse proxy — single public SPCS endpoint at port 9000 Routes /api/* to the backend container and all other paths to the frontend container. Configuration is generated at container startup from a template via envsubst, with FRONTEND_SERVICE and BACKEND_SERVICE injected as environment variables. Eliminates CORS entirely in SPCS — all traffic passes through one origin.
Snowflake SPCS — Managed container hosting platform inside Snowflake All three containers run co-located in a single service spec. SPCS automatically mounts an OAuth token at /snowflake/session/token inside the backend container, enabling zero-credential database authentication. The public endpoint is exposed via a single routerendpoint on port 9000.

5. CI / CD GitHub Actions

WorkflowTriggerPurpose
CI (ci.yml) Push to main / API_Tests; PR to main Runs backend pytest (44 tests) and frontend Vitest (20 tests) in parallel on ubuntu-latest. Fails the commit if any test fails. Uses pip and npm dependency caching for fast repeat runs.
Deploy Group (deploy-group.yml) Manual (workflow_dispatch) Builds and pushes all three Docker images to the Snowflake registry, then recreates the SPCS service for a given group number. Accepts a fork URL as input to deploy intern forks without modifying the workflow.
Pre-warm (prewarm.yml) Manual Pre-warms SPCS compute pools before a session to reduce cold-start latency.
Resume / Suspend (resume-group.yml, suspend-group.yml) Manual Starts or suspends a group's SPCS service to manage compute costs outside active session hours.

Pre-push Git hook

A shell-based pre-push hook (hooks/pre-push) is committed to the repository and installed locally by each developer via hooks/install-hooks.sh (macOS) or hooks/install-hooks.bat (Windows). It runs both test suites before every git push, blocking the push if either suite fails. Works on Windows via Git's bundled bash. Can be bypassed with git push --no-verify in emergencies.

6. Testing pytest · Vitest

TechnologyVersionScopeDetails
pytest 8.3.5 Backend API integration tests 44 test cases across 7 endpoint classes in backend/test_api.py. Fixtures in conftest.py create a TestClient wired to the SQLite database. A second fixture patches main.CLIENT_VALIDATION in-place to test the SPCS auth path without a module reload.
httpx 0.28.1 Required transport for FastAPI's TestClient Tests run fully in-process — no live server is started. Allows CI to run the full backend test suite in under 2 seconds.
Vitest ^3.2.4 Frontend unit tests 14 tests for the API client (api.test.js) and 6 component tests for ServiceStatus. Integrated with Vite's config — test environment, globals, and setup files are declared in vite.config.js.
@testing-library/react ^16.3.0 React component rendering and DOM querying in tests Provides render, screen, and waitFor utilities. Encourages testing from the user's perspective (visible text, attributes) rather than internal component state.
@testing-library/jest-dom ^6.6.3 Custom DOM matchers for Vitest assertions Adds matchers like toBeInTheDocument() and toHaveAttribute(). Registered globally via src/setupTests.js.
jsdom ^26.1.0 Browser DOM emulation for Vitest Provides a full DOM environment for React component tests running in Node. Configured as the Vitest test environment in vite.config.js (environment: "jsdom").

Test strategy summary

  • No backend mocking — backend tests run real SQL queries against novacart_gold.db. This validates the full stack from HTTP request to SQL result, including query correctness, sort order, and data types.
  • Full frontend isolation — frontend tests stub fetch globally via vi.stubGlobal and mock the API module via vi.mock. No network calls are made; tests are fast and deterministic.
  • Two-gate model — pre-push hook provides a fast local gate; GitHub Actions CI provides the authoritative gate on the shared branch. A push that bypasses the hook is still caught by CI.
